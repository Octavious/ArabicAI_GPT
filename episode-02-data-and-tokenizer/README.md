## Three Big Decisions in This Episode

This episode is a decision tree. Each choice cascades into the next.

### Decision 1: How big a model can we actually train?

The naive answer: "I have 6 GB, so I can fit a 1.5 billion parameter model since each FP32 parameter is 4 bytes."

The real answer: **a 12-million-parameter model.** Here's the math.

#### Every Parameter Lives in Memory Four Times

During training, each "dial" in the model takes up four slots in memory:

| Storage | What it is | Plain version | Cost |
|---------|------------|---------------|------|
| 1. The parameter | The dial value | What the model has learned | 4 bytes |
| 2. The gradient | Which way to turn the dial | The "feedback signal" from this training step | 4 bytes |
| 3. Adam's momentum | A running average of recent gradients | "Which direction has this dial been moving lately?" | 4 bytes |
| 4. Adam's variance | A running average of squared gradients | "How wildly has this dial been jumping around?" | 4 bytes |

**Total: 16 bytes per parameter, just for these four.**

So a 1 billion parameter model needs 16 GB just for these four pieces. Way more than our 6 GB has, before counting anything else.

#### And Activations Are Often Bigger

Activation memory — the intermediate "scratch work" each layer keeps for backpropagation — typically dwarfs the model itself. It scales with `batch_size × sequence_length × n_embd × n_layer`, plus a quadratic term inside attention that scales with `sequence_length²`.

For our model with batch 32, sequence length 256, embed 384, 6 layers: activations come to **roughly 1.5 GB during training**.

#### The 6 GB Reality

| Eating GPU memory | Approximate |
|-------------------|-------------|
| Windows + Chrome + OneDrive | ~1 GB |
| PyTorch overhead | ~0.5 GB |
| Activations during training | ~1.5 GB |
| Available for model + Adam state | **~3 GB** |

3 GB ÷ 16 bytes per parameter = **~190 million parameters maximum**, in absolute terms.

We pick 12 million — well below the ceiling — for three reasons:

1. **Training time.** A 12 M model trains in 2 hours. A 190 M model would take 16+ hours. Fast iteration matters when learning.
2. **The data doesn't need it.** TinyStories is simple enough that 12 M produces coherent output. Bigger wouldn't help.
3. **Headroom.** We want room to bump batch size or context length without instantly OOMing.

### Decision 2: What dataset should we feed it?

A small model can't handle internet-scale diversity. With only 12 M parameters worth of patterns, we need:

- **Restricted vocabulary** — a few thousand common words
- **Consistent genre** — one style throughout
- **Repetitive structure** — patterns that recur many times so the model can learn them
- **Big enough** — millions of examples

We picked **TinyStories** (Microsoft Research, 2023). It's 2.12 million short children's stories generated by GPT-3.5/4 with one rule: only use vocabulary a 3-year-old understands.

Why not other datasets:

| Dataset | Why we passed |
|---------|---------------|
| OpenWebText | Internet text — too diverse, needs ~50K vocab |
| The Pile | Same issue. Plus it's 800 GB. |
| Wikipedia | Encyclopedia style is dense; many rare named entities |
| Shakespeare | Karpathy's classic — fun but only 1 MB, too small for our model size |
| Code (Python, etc.) | Great alternative if you want a code bot instead |
| **TinyStories** ✓ | **Right scope, right size, right style** |

### Decision 3: How do we convert text into numbers?

Neural networks don't read text. They read numbers. We need to convert every word, space, and punctuation mark into a number — this is **tokenization**.

#### Three Bad Approaches

| Approach | Problem |
|----------|---------|
| One number per word | English has ~170K distinct words. Plus typos, names, new coinages. Vocabulary explodes. Anything new becomes `<UNK>`. |
| One number per character | Only ~100 tokens needed. But "tokenization" becomes 12 tokens. Sequences become 5× longer. Training crawls. |
| Top 50K words only | Combines both problems. Common words bloat the table; rare words still get lost. |

We need something **between** words and characters.

#### Byte-Pair Encoding (BPE)

BPE was originally a 1994 data compression algorithm, repurposed for tokenization in 2015. The idea: let the data tell us what the right "units" are.

The algorithm:

1. Start with every character as a token
2. Find the most common adjacent pair of tokens
3. Merge that pair into a new token
4. Repeat until vocabulary reaches your target size

After many merges, common words become single tokens; rare words stay as multiple pieces. **No unknown tokens, ever.**

#### Why a 4,096 Vocabulary

| Vocab size | Used by | Tradeoff |
|-----------|---------|----------|
| 1,024 | experimental | Sequences become long; common words split |
| **4,096** ✓ | **our project** | **Balanced for TinyStories' simple vocabulary** |
| 32,000 | LLaMA | Large but efficient; covers most common words |
| 50,257 | GPT-2 | Good for general internet text |
| 128,000 | GPT-4 | Multi-language, code, long contexts |

The deciding factor: every token needs a 384-number "meaning vector" in the embedding table. Table size = `vocab × n_embd`.

- Vocab 4,096 × 384 = **1.6 M params** (manageable)
- Vocab 50,257 × 384 = **19.3 M params** (more than our entire model budget)

If we used GPT-2's vocabulary, embeddings alone would eat our whole parameter budget.

## Three Engineering Details Worth Understanding

### Why uint16 instead of int64

Token IDs are integers. Python's default integer storage is 64-bit (8 bytes). But our largest token ID is 4,095, which fits in 16 bits (2 bytes).

Using `uint16` makes the file **4× smaller**:

- `int64`: 3.9 GB
- `uint16`: 970 MB

This matters for both disk space and load speed.

### Why memory-mapped files

Instead of loading the entire 970 MB into RAM, we use NumPy's `memmap`. This tells the OS "load pages from disk only when accessed." We get the speed of in-memory access without the RAM cost.

Critical for scaling up. If you later train on larger datasets (10 GB+), `memmap` is what makes that possible without buying more RAM.

### Why parallel tokenization

Tokenizing 2 million stories one at a time would take ~30 minutes on CPU. Using HuggingFace's `dataset.map(num_proc=8)`, we run tokenization across 8 CPU cores in parallel. The job drops to ~5 minutes.

#### A Windows Gotcha

Python's multiprocessing on Windows works by re-importing your script in each worker process. Without protection, you get an infinite loop:

```
RuntimeError: An attempt has been made to start a new process before
the current process has finished its bootstrapping phase.
```

The fix: wrap your main code in `if __name__ == '__main__':`. The script in this folder already does this — but if you adapt the code for other projects, don't forget it.

## Why Two Files (train.bin and validation.bin)?

We deliberately **hold out 22,000 stories** the model will never see during training. They go into `validation.bin`.

Without a held-out set, we couldn't tell whether the model is **learning** real language patterns (which would generalize to new text) or just **memorizing** the training stories (which wouldn't).

If the model hits very low loss on training data but high loss on validation data, it's memorizing — overfitting. The validation set is our honest measure.

We'll explore this much more in Episode 06 ("Watching it learn"), but the data split happens here.

## Common Issues

### `Tokenizer training is taking forever`

It's CPU-bound and shouldn't exceed 10 minutes on a modern machine. If it's been over 15 minutes, check Task Manager — Python should be using ~100% of one CPU core. If not, the iterator is being starved (usually a memory issue with the dataset).

### `prepare_data.py crashes with multiprocessing error`

You're missing the `if __name__ == '__main__':` wrapper. The script in this folder has it; if you adapted the code, add it.

### `train.bin is much smaller than 970 MB`

Tokenization may have failed silently for many stories. Check the first lines of `prepare_data.py` output for warnings or errors.

### `np.memmap raises permission error`

Another process is holding the file open. Close any Python interpreter or text editor that has the file open and retry.

### `inspect_data.py prints garbage`

The token IDs aren't being decoded correctly. Most likely cause: tokenizer file mismatch. Make sure `tinystories_tokenizer.json` was actually produced by `train_tokenizer.py` in this same project (not copied from elsewhere).
